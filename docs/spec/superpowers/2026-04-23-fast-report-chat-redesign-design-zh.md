# 快速报告对话重构 (Fast Report Chat Redesign)

## 摘要

本文档详述了将当前仓库对话体验重构为快速、证据驱动的报告工作区的方案。新体验将传统的对话气泡替换为左侧的报告栈和右侧同步的证据栏，同时保留 `FloatingAssistant`（悬浮助手）作为后续提问的入口。

设计目标是产出具备以下特征的答案：

- 易于快速浏览
- 基于代码和仓库结构
- 易于导航回源证据
- 通过短期持久化实现可复用
- 通过链接到生成的 Wiki 内容实现可扩展性

该设计还将在新的快速报告流程完成后，移除现有的流式对话 UI。

## 目标

- 用非对话式的快速报告体验取代当前的对话页面。
- 保留 `FloatingAssistant` 作为初始提问和后续提问的统一入口。
- 将每个答案渲染为结构化的 Markdown 报告章节，而非对话气泡。
- 在右侧证据栏中显示所有支持的代码证据块，按答案中出现的顺序排列。
- 允许 Markdown 引用深层链接到证据栏并高亮相应的块。
- 将生成的快速报告通过稳定 URL 持久化保留 7 天。
- 重新打开持久化的报告时无需额外的 LLM 调用。
- 使用混合检索以保证覆盖率，但最终结论必须依赖代码证据或仓库结构证据。
- 自动附带相关的生成 Wiki 页面作为延伸阅读。
- 支持将 Mermaid 图表作为一等公民的报告内容，以提升理解效果。

## 非目标

- 保留现有的基于气泡的对话 UI。
- 保留对话历史作为聊天记录。
- 将生成的 Wiki 页面视为主要证据。
- 在此阶段引入除 7 天 TTL 之外的永久性长期报告存储。
- 构建一个带有认证、权限或多用户协作的通用报告共享系统。

## 产品方向

新体验不再是一个对话窗口，而是一个支持迭代提问的报告工作区。

用户通过 `FloatingAssistant` 提问，然后跳转到快速报告页面，该页面展示：

- 左侧的报告栈 (Report Stack)
- 右侧同步的证据栏 (Evidence Rail)
- 始终可用的 `FloatingAssistant` 覆盖层，用于后续提问

每一个后续提问都会在栈中生成一个新的报告章节，而不是一条新的对话消息。页面维持的是阅读流工作模式，而非即时消息模式。

## 用户体验

### 入口流程

- `FloatingAssistant` 保持可见，作为主要的提问入口。
- 提交问题后将用户路由至快速报告页面。
- 如果页面已包含当前报告 URL 的持久化章节，则立即恢复它们。
- 新问题会追加一个新的报告章节，而不是替换整个页面。

### 布局

快速报告页面采用双栏布局：

- 左栏：`报告栈 (Report Stack)`
- 右栏：`证据栏 (Evidence Rail)`

左栏是主要的阅读区域，右栏是主要的验证区域。

### 报告栈 (Report Stack)

每个答案渲染为一个结构化的 Markdown 章节，而非气泡。

每个章节可包含：

- 标题
- 摘要
- 丰富的 Markdown 正文
- Mermaid 图表
- 相关的 Wiki 链接
- 章节状态

报告栈按时间顺序排列。用户可以向上滚动查看旧章节并重新激活它们。当前激活的章节决定了右侧证据栏的焦点。

### 证据栏 (Evidence Rail)

证据栏显示当前激活报告章节所引用的所有证据块。

证据块的展示方式：

- 按引用出现的顺序排列
- 不设固定上限
- 每个引用都有一个稳定的锚点

每个证据块：

- 显示引用的代码范围
- 默认包含上方 3 行和下方 3 行的上下文
- 支持通过交互单次扩展 15 行
- 支持折叠回默认上下文
- 支持从 Markdown 导航时的视觉聚焦

### 引用导航

报告正文中的 Markdown 引用被渲染为结构化链接而非纯文本。

当用户点击引用时：

- 证据栏滚动到相应的证据块
- 该证据块被高亮
- 目标块成为当前的焦点区域

### FloatingAssistant 覆盖层行为

`FloatingAssistant` 在快速报告页面上依然可用，用于后续提问。

为了防止它遮挡页面底部内容：

- 可滚动的页面容器必须预留与助手渲染高度相等的底部安全空间。
- 最后的报告章节必须停止在助手覆盖层之上。
- 最后的证据块也必须停止在助手覆盖层之上。
- 预留空间必须能够响应移动端布局中助手高度的变化。

必须移除旧的页内底部输入框。

## 报告结构

报告的 Markdown 应比当前的对话输出更具结构性。渲染器应支持更丰富的默认章节模板，并省略与当前查询无关的部分。

推荐的报告标题：

- `概述 (Overview)`
- `核心实现组件 (Core Implementation Components)`
- `关键实现细节 (Key Implementation Details)`
- `执行流程 / 步骤 (Execution Flow / Steps)`
- `配置 (Configuration)`
- `使用场景 (Use Cases)`
- `备注 (Notes)`
- `进一步探索 (Further Explore)`

生成层可以省略空的标题，但提示词（Prompt）和 Schema 应鼓励这种结构。

## 检索与证据模型

### 检索层

系统应从四个互不重叠的上下文层进行检索。

#### 1. 仓库结构层 (Repository Structure Layer)

此层覆盖全仓库范围的结构信号：

- 目录树
- 包与模块边界
- 入口点
- 文件集群
- 依赖图信息
- 大纲锚点 (Outline anchors)

`大纲锚点` 是此层的一部分，不应被视为独立的检索类别。

#### 2. 代码证据层 (Code Evidence Layer)

此层包含可直接检查的实现证据：

- 符号定义
- 实现切片
- 调用点
- 引用点
- 类型与接口
- 配置读写点
- 测试断言点

此层不限于符号名称，必须包含实现细节和关系细节。

#### 3. 语义检索层 (Semantic Retrieval Layer)

此层包含有助于理解代码的语义上下文：

- RAG 分块 (Chunks)
- 文档字符串 (Docstrings)
- 行内注释
- README 段落
- 其他自然语言解释片段

此层有助于解释含义，但不能独立作为关键结论的依据。

#### 4. 整理知识层 (Curated Knowledge Layer)

此层包含先前合成的项目知识：

- 生成的 Wiki 页面
- 页面用途 (Page purposes)
- 先前的结构化摘要

此层用于组织和进一步阅读，而非最终结论的仲裁依据。

### 检索策略

所有四个层应并行检索。

仲裁规则如下：

- 最终结论必须由 `代码证据层` 或 `仓库结构层` 支持。
- `语义检索层` 可用于澄清或连接证据。
- `整理知识层` 可用于丰富组织结构和延伸阅读。

这在保证覆盖率的同时，防止了无根据的叙事偏差。

## 报告生成流水线

### 1. 问题分类

将原始用户问题转换为轻量级的结构化意图：

- 问题类型
- 目标子系统或符号
- 预期回答形式
- 可能的证据形态

问题类型示例：

- 架构
- 执行流程
- 实现位置
- 配置
- 错误处理
- 测试
- 依赖关系

### 2. 检索

从上述四个层检索候选内容。

检索阶段应倾向于：

- 实现切片优于全文件转储
- 流程问题倾向于边界和入口文件
- 行为问题倾向于配置触达点
- 架构问题倾向于依赖和结构信号

### 3. 证据仲裁

在最终 Markdown 组装前，系统应修剪或降级无支持的结论。

允许的结果：

- `supported`（支持）：由代码证据或仓库结构证据支持
- `qualified`（有限）：貌似合理但不完整，明确标记为不确定
- `dropped`（丢弃）：从最终报告中排除

### 4. 报告组装

生成包含以下内容的结构化 Markdown：

- 章节标题
- 叙事合成
- 行内证据引用
- 可选的 Mermaid 图表
- 相关的 Wiki 引用

### 5. 证据打包

对于 Markdown 中的每个行内引用：

- 创建或复用一个稳定的引用 ID
- 附带匹配的证据块载荷
- 保持引用顺序

## 数据模型

### 快速报告 (Fast Report)

每个生成的报告应有一个唯一的持久化记录。

建议字段：

- `id`
- `repo_id`
- `commit_sha`
- `created_at`
- `expires_at`
- `status`
- `active_section_id`

### 报告章节 (Report Section)

每个提交的问题产出一个报告章节。

建议字段：

- `id`
- `report_id`
- `query`
- `title`
- `summary`
- `markdown`
- `citations`
- `related_wiki_pages`
- `related_diagrams`
- `created_at`
- `status`

### 引用 (Citation)

每个引用必须有一个稳定的身份，可在 Markdown 渲染器和证据栏之间共享。

建议字段：

- `id`
- `section_id`
- `file_path`
- `start_line`
- `end_line`
- `label`
- `kind`
- `reason`
- `score`

### 证据块 (Evidence Block)

证据块是为右侧栏准备的渲染就绪的引用载荷。

建议字段：

- `citation_id`
- `snippet_start`
- `snippet_end`
- `full_start`
- `full_end`
- `default_context`
- `expanded_context`
- `is_collapsed`
- `code`
- `symbol_path`

### 相关 Wiki 链接

建议字段：

- `slug`
- `title`
- `reason`

### 相关图表

Mermaid 图表应作为一等公民的报告内容存储。

建议字段：

- `id`
- `section_id`
- `title`
- `type`
- `source`
- `caption`
- `reason`
- `citations`
- `placement`

支持的图表类型应包括产品当前渲染流水线支持的所有 Mermaid 类型，不仅限于依赖图。

## 持久化与 TTL

快速报告应持久化保留 7 天。

### URL 模型

每个报告必须有一个格式如下的稳定 URL：

- `/{owner}/{repo}/fast/{report_id}`

### 重新打开行为

在 TTL 内重新打开报告必须：

- 加载持久化的报告元数据
- 加载持久化的报告章节
- 加载持久化的 Markdown 和引用映射
- 加载持久化的图表载荷
- 在不调用 LLM 的情况下重新渲染页面

### 过期

7 天后：

- 报告被视为已过期
- 用户可能会看到过期状态和重新生成的选项
- 重新生成会产出新的输出，而不是静默修改已过期的结果

### Commit 绑定

报告必须绑定到生成时使用的 Commit SHA。

这是为了确保：

- 旧报告保持证据一致性
- 仓库更新后引用不会发生漂移
- 证据渲染可以被视为已知分析快照的重放

## Wiki 链接策略

相关的 Wiki 页面应作为扩展路径附带，而非作为主要证明来源。

推荐的关联顺序：

1. 明确的文件到页面的重合
2. 标题或术语的相似性
3. 同一子系统内的结构接近性

每个报告章节应附带一小组高信号的 Wiki 链接，而非长长的链接列表。

## Mermaid 策略

仅当图表具有解释价值时才生成 Mermaid 图表。

良好的触发场景：

- 跨模块执行流
- 异步或有状态的控制流
- 分层依赖关系
- 实体关系
- 配置到运行时的路径映射

图表是证据组织工具，而非装饰性内容。

## API 与后端变更

### 新的快速报告 API 表面

当前的面向对话的表面应被面向报告的表面取代。

建议的逻辑操作：

- 创建快速报告
- 向报告追加章节
- 通过 ID 获取持久化报告
- 获取报告章节载荷

具体的路由命名可以遵循现有 API 规范，但载荷模型不应复用对话消息的 DTO。

### 生成服务

创建一个独立的快速报告生成路径，而非复用旧的对话响应契约。

生成器可以复用：

- AST 输出
- 依赖图输出
- RAG 索引
- 生成的 Wiki 数据
- Mermaid 清洗与渲染路径

但它应该发出专用的结构化报告 Schema。

## 前端变更

### 替换 ChatPanel

现有的 `ChatPanel` 组件应被移除，并替换为快速报告工作区组件。

建议的 UI 拆分：

- `FastReportPage` 外壳
- `ReportStack`
- `ReportSection`
- `CitationLink`
- `EvidenceRail`
- `EvidenceBlock`

### FloatingAssistant 集成

`FloatingAssistant` 应继续将问题路由至快速报告流程。

该组件可能需要进行微小的模式更新，但应保持作为用户可见的提问入口。

### 底部安全间距

页面外壳应测量渲染的 `FloatingAssistant` 高度，并将其暴露给滚动容器。

这可以通过以下方式实现：

- CSS 变量驱动的 padding
- 测量出的占位元素
- 或共享的布局上下文 (Layout Context)

实现方式灵活，但必须保证该行为。

## 迁移与删除计划

一旦快速报告流程端到端工作正常：

- 移除现有的基于气泡的对话页面
- 移除旧的底部对话输入框
- 移除对话专用的流式 UI 契约
- 移除废弃的前端状态和消息渲染路径

流式生成内部可能依然存在，但它应表现为报告章节的生成状态，而非逐字输出的对话。

## 测试策略

### 前端

- 点击引用能够滚动到正确的证据块
- 证据块高亮状态正确更新
- `Expand +15`（扩展 15 行）和 `Collapse`（折叠）功能正常
- 底部内容在 `FloatingAssistant` 之上保持可见
- 持久化报告重新加载时在无网络生成调用的情况下渲染
- 激活章节能够正确切换证据栏

### 后端

- 报告生成能够持久化预期的 Schema
- 强制执行 TTL 过期
- 报告重新加载不调用 LLM
- 保留 Commit SHA 绑定
- 在仲裁期间降级或移除无支持的结论
- 确定性地附带相关的 Wiki 链接

### 端到端

- 从 `FloatingAssistant` 提交问题
- 跳转到快速报告页面
- 看到章节内容和同步的证据
- 在 TTL 内重新打开报告 URL 而不触发重新生成
- 提出后续问题并看到追加的新章节

## 风险

- 如果证据载荷未严格绑定到 Commit SHA，可能会发生引用漂移。
- 如果生成规则过于宽松，可能会过度生成 Mermaid 图表。
- 如果四个检索层划分不清晰，可能会发生检索重叠。
- 如果证据扩展是通过重复读取文件且不带缓存实现的，可能会增加渲染复杂度。
- 如果在移动端宽度下未稳健地测量 `FloatingAssistant` 高度变化，可能会导致 UI 退化。

## 验收标准

- 当前对话页面不再渲染基于气泡的交流 UI。
- `FloatingAssistant` 依然是后续提问的入口。
- 每个问题产出一个结构化的报告章节，而非对话消息。
- 报告栈和证据栏通过引用 ID 保持同步。
- 所有引用的证据块按引用顺序显示在证据栏中。
- 证据块默认为 `±3` 行，每次交互可扩展 `15` 行。
- 页面底部内容在悬浮覆盖层之上保持可见。
- 报告在唯一的 URL 下持久化保留 7 天。
- 重新打开有效的报告 URL 不会触发新的 LLM 生成。
- 最终结论基于代码证据或仓库结构证据。
- 相关的 Wiki 内容作为延伸阅读出现，而非主要证据。
- 旧有的对话 UI 代码路径可以安全移除。
