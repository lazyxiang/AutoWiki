# 快速报告对话重构 (Fast Report Chat Redesign)

## 摘要

本文档详细说明了将当前的仓库对话体验重构为快速、证据驱动的报告工作区的方案。新的体验将取代传统的对话气泡，采用左侧“报告栈 (Report Stack)”和右侧同步的“证据轨 (Evidence Rail)”布局，同时保留 `FloatingAssistant` 作为后续提问的入口。

设计目标是生成具有以下特征的答案：

- 易于快速扫描
- 基于代码和仓库结构
- 易于导航回源代码证据
- 通过短期持久化实现可复用性
- 通过链接到生成的 Wiki 内容实现可扩展性

在新的快速报告流程完成后，本设计还将移除现有的流式对话 UI。

## 目标

- 用非对话式的快速报告体验取代当前的对话页面。
- 保留 `FloatingAssistant` 作为初始提问和后续提问的共享入口。
- 将每个答案渲染为结构化的 Markdown 报告章节，而非对话气泡。
- 在右侧的证据轨中显示所有支撑代码证据块，并按其在答案中出现的顺序排列。
- 允许 Markdown 引用深层链接到证据轨并高亮对应的代码块。
- 将生成的快速报告持久化 7 天，并提供稳定的 URL。
- 无需额外的 LLM 调用即可重新打开已持久化的报告。
- 以确定性的仓库分析、关键词检索和有界的代码图扩展作为主要的证据路径，同时要求最终结论必须有代码证据或仓库结构证据支撑。
- 自动将相关的生成 Wiki 页面作为扩展阅读附后。
- 在有助于理解时，支持将 Mermaid 图表作为报告的一等内容。

## 非目标

- 保留现有的基于气泡的对话 UI。
- 将对话历史保留为聊天记录。
- 将生成的 Wiki 页面视为主要证据。
- 在本阶段引入超过 7 天 TTL 的永久性长期报告存储。
- 构建一个包含权限、授权或多用户协作的通用报告共享系统。

## 产品方向

新的体验不是一个对话窗口，而是一个带有迭代提问功能的“报告工作区”。

用户通过 `FloatingAssistant` 提问，然后跳转到快速报告页面，该页面呈现：

- 左侧的报告栈 (Report Stack)
- 右侧的同步证据轨 (Evidence Rail)
- 始终可用的 `FloatingAssistant` 悬浮窗，用于后续提问

每个后续提问都会在栈中生成一个新的报告章节，而不是一条新的对话消息。页面保留的是“阅读工作流”而非“即时通讯工作流”。

## 用户体验

### 入口流程

- `FloatingAssistant` 保持可见，作为主要的问题输入界面。
- 提交问题后，用户被引导至快速报告页面。
- 如果该页面对应的报告 URL 已包含持久化的报告章节，则立即恢复显示。
- 新问题将追加一个新的报告章节，而不是替换整个页面。

### 布局

快速报告页面采用两栏布局：

- 左栏：报告栈 (Report Stack)
- 右栏：证据轨 (Evidence Rail)

左栏是主要阅读区，右栏是主要验证区。

### 报告栈 (Report Stack)

每个答案都被渲染为一个结构化的 Markdown 章节，而非气泡。

每个章节可包含：

- 标题
- 摘要
- 丰富的 Markdown 正文
- Mermaid 图表
- 相关的 Wiki 链接
- 章节状态

报告栈按时间顺序排列。用户可以滚动回旧章节并重新激活它们。活动章节控制右侧证据轨的焦点。

### 证据轨 (Evidence Rail)

证据轨显示活动报告章节引用的所有证据块。

证据块显示规则：

- 按照引用出现的顺序排列
- 不设固定数量限制
- 每个引用都有稳定的锚点

每个证据块：

- 显示引用的代码范围
- 默认包含上下各 3 行的上下文
- 支持每次点击扩展 15 行
- 支持折叠回默认上下文
- 支持在从 Markdown 导航过来时显示视觉焦点

### 引用导航

报告正文中的 Markdown 引用被渲染为结构化链接，而非原始文本。

当用户点击引用时：

- 证据轨滚动到对应的证据块
- 该证据块被高亮显示
- 目标块成为当前的活动焦点区域

### FloatingAssistant 悬浮窗行为

`FloatingAssistant` 在快速报告页面上继续可用，用于后续提问。

为防止其遮挡页面底部内容：

- 可滚动的页面容器必须预留等于助手高度的底部安全空间。
- 最后的报告章节必须停在助手悬浮窗上方。
- 最后的证据块也必须停在助手悬浮窗上方。
- 预留空间必须能够响应移动端布局下助手高度的变化。

现有的页内底部输入框 (Composer) 必须移除。

## 报告结构

报告的 Markdown 应比当前的对话输出更具结构性。渲染器应支持更丰富的默认章节模板，并省略与当前查询无关的部分。

推荐的报告标题：

- `概述 (Overview)`
- `核心实现组件 (Core Implementation Components)`
- `关键实现细节 (Key Implementation Details)`
- `执行流程 / 步骤 (Execution Flow / Steps)`
- `配置 (Configuration)`
- `使用场景 (Use Cases)`
- `说明 (Notes)`
- `进一步探索 (Further Explore)`

生成层可以省略空的标题，但提示词 (Prompt) 和 Schema 应鼓励这种结构。

实现应保持稳定的内部规范标题键 (Heading Keys)，同时根据检测到的报告语言渲染可见的标题文本。这允许生成器接受英文或中文的标题标签，同时将结果归一化为一种稳定的内部形式。

## 语言策略

快速报告的输出应遵循用户问题的检测语言。

- 默认为英文。
- 检测到问题为中文时切换为简体中文。
- 代码标识符、类名、函数名、文件路径、配置键及其他仓库原生标记保持其原始英文形式。
- 无论输出语言如何，内部 JSON 键和规范章节标识符均保持英文。

初始实现不应引入持久化的 `report_language` 字段。语言应在生成时按每个问题进行推断。

## 检索与证据模型

### 检索层

系统应从四个互不重叠的上下文层进行检索。

#### 1. 仓库结构层 (Repository Structure Layer)

此层覆盖仓库范围内的结构化信号：

- 目录树
- 包与模块边界
- 入口点 (Entry points)
- 文件簇 (File clusters)
- 依赖图信息
- 大纲锚点 (Outline anchors)

`大纲锚点` 是此层的一部分，不应被视为独立的检索类别。

#### 2. 代码证据层 (Code Evidence Layer)

此层包含可直接检查的实现证据：

- 符号定义
- 实现切片 (Implementation slices)
- 调用点 (Call sites)
- 引用点 (Reference sites)
- 类型与接口
- 配置读写点
- 测试断言点

此层不限于符号名称，必须包含实现细节和关系细节。

#### 3. 解释性上下文层 (Interpretive Context Layer)

此层包含有助于解释代码的说明性上下文：

- 文档字符串 (Docstrings)
- 行内注释
- README 段落
- 标题级文档片段
- 从确定性候选者中选出的其他自然语言说明片段

此层有助于解释含义，但不能独立作为关键结论的依据。

#### 4. 精选知识层 (Curated Knowledge Layer)

此层包含先前合成的项目知识：

- 生成的 Wiki 页面
- 页面用途
- 先前的结构化摘要

此层用于组织和进一步阅读，不用于最终结论的仲裁。

### 检索策略

在经过轻量级的搜索规划后，应并行检索所有四个层。

仲裁规则为：

- 最终结论必须由 `代码证据层` 或 `仓库结构层` 支撑。
- `解释性上下文层` 可以澄清或连接证据。
- `精选知识层` 可以丰富组织结构和扩展阅读。

这在保证覆盖范围的同时，防止了无证据支持的叙述偏差。

初始实现应避免在快速报告路径中使用基于嵌入 (Embedding) 和向量搜索的检索。相反，检索应由确定性的仓库信号、关键词搜索、符号查找以及有界的依赖/引用扩展驱动。

## 报告生成流水线

### 1. 问题语言检测

在任何 LLM 生成步骤之前，检测输入问题的语言。

规则：

- 默认为英文。
- 本地从问题文本检测中文。
- 使用检测到的语言来控制标题、摘要、说明和 Markdown 的生成。

### 2. 搜索计划生成

使用轻量级的第一次 LLM 调用将原始问题转换为结构化的搜索计划。

搜索计划应捕捉：

- 问题类型
- 目标子系统或符号
- 预期的答案形式
- 可能的证据形态
- 英文关键词提示
- (必要时) 中文关键词提示
- 符号提示
- 路径提示
- 检索模式

问题类型示例：

- 架构
- 执行流程
- 实现位置
- 配置
- 错误处理
- 测试
- 依赖关系

### 3. 确定性检索与扩展

从上述四个层检索候选者，不依赖向量相似度。

检索阶段应优先考虑：

- 实现切片优于整文件转储。
- 对于流程类问题，优先考虑边界和入口文件。
- 对于行为类问题，优先考虑配置接触点。
- 对于架构类问题，优先考虑依赖和结构信号。
- 优先考虑符号定义和引用点，而非宽泛的文件级摘录。

代码证据检索应结合：

- 路径和文件名的关键词匹配。
- 符号和签名的匹配。
- 文档字符串和 README 标题的匹配。
- 从匹配的种子文件进行有界的依赖扩展。
- (可用时) 进行有界的符号/引用扩展。

对于执行流程和依赖类问题，生成器应捕捉一组小型的调用链式证据，并明确其角色，如 `entrypoint` (入口)、`callee` (被调用者)、`config_touchpoint` (配置触点)、`interface` (接口) 或 `test_assertion` (测试断言)。

### 4. 证据仲裁

在最终 Markdown 组装之前，系统应修剪或降级无支撑的结论。

允许的结果：

- `supported` (支撑)：有代码证据或仓库结构证据支撑。
- `qualified` (有限支撑)：合理但不完整，明确标记为不确定。
- `dropped` (舍弃)：从最终报告中剔除。

### 5. 报告组装

生成包含以下内容的结构化 Markdown：

- 章节标题
- 叙述性合成
- 行内证据引用
- (可选) Mermaid 图表
- 相关的 Wiki 引用

### 6. 证据打包

对于 Markdown 中的每个行内引用：

- 创建或复用稳定的引用 ID。
- 附加匹配的证据块负载 (Payload)。
- 保留引用顺序。

### 7. 分析追踪 (Analysis Trace)

在最终 Markdown 就绪之前，系统应流式传输轻量级的分析追踪，解释当前正在检查哪些文件以及原因。

追踪信息应足以支撑临时的预报告 UI 状态，而非完整的调试记录。

## 数据模型

### 快速报告 (Fast Report)

每个生成的报告应具有唯一的持久化记录。

建议字段：

- `id`
- `repo_id`
- `commit_sha`
- `created_at`
- `expires_at`
- `status`
- `active_section_id`

### 报告章节 (Report Section)

每个提交的问题产生一个报告章节。

建议字段：

- `id`
- `report_id`
- `query`
- `title`
- `summary`
- `markdown`
- `analysis_trace`
- `citations`
- `related_wiki_pages`
- `related_diagrams`
- `created_at`
- `status`

### 引用 (Citation)

每个引用必须具有稳定的标识，以便在 Markdown 渲染器和证据轨之间共享。

建议字段：

- `id`
- `section_id`
- `file_path`
- `start_line`
- `end_line`
- `label`
- `kind`
- `reason`
- `score`

### 证据块 (Evidence Block)

证据块是用于右侧轨道的渲染就绪型引用负载。

建议字段：

- `citation_id`
- `snippet_start`
- `snippet_end`
- `full_start`
- `full_end`
- `default_context`
- `expanded_context`
- `is_collapsed`
- `code`
- `symbol_path`

### 分析追踪 (Analysis Trace)

建议字段：

- `phase`
- `language`
- `search_plan`
- `files`

每个文件条目应包含：

- `path`
- `role`
- `reason`
- `status`

### 相关 Wiki 链接

建议字段：

- `slug`
- `title`
- `reason`

### 相关图表

Mermaid 图表应作为一等报告内容存储。

建议字段：

- `id`
- `section_id`
- `title`
- `type`
- `source`
- `caption`
- `reason`
- `citations`
- `placement`

支持的图表类型应包括产品渲染流水线当前支持的所有 Mermaid 图表类型，不仅限于依赖图。

## 持久化与生存时间 (TTL)

快速报告应持久化 7 天。

### URL 模型

每个报告必须具有如下形式的稳定 URL：

- `/{owner}/{repo}/fast/{report_id}`

### 重新打开行为

在 TTL 内重新打开报告必须：

- 加载持久化的报告元数据。
- 加载持久化的报告章节。
- 加载持久化的 Markdown 和引用映射。
- 加载持久化的图表负载。
- 重新渲染页面，无需调用 LLM。

### 过期

7 天后：

- 报告被视为过期。
- 用户可能会看到过期状态和重新生成的选项。
- 重新生成会创建全新的输出，而不是静默修改已过期的结果。

### 提交绑定 (Commit Binding)

报告必须绑定到生成时使用的 Commit SHA。

这是为了确保：

- 旧报告保持证据一致性。
- 仓库更新后引用不会偏移。
- 证据渲染可以被视为对已知分析快照的重放。

## Wiki 链接策略

相关的 Wiki 页面应作为扩展路径附加，而不是作为主要证明来源。

建议的附加顺序：

1. 明确的文件与页面重合。
2. 标题或术语相似性。
3. 同一子系统内的结构接近度。

每个报告章节应附加少量高信号的 Wiki 链接，而非长篇链接列表。

## Mermaid 策略

仅当图表具有解释价值时才生成 Mermaid 图表。

良好的触发场景：

- 跨模块执行流程。
- 异步或有状态的控制流。
- 分层依赖关系。
- 实体关系。
- 从配置到运行时的路径映射。

图表是证据组织工具，而非装饰性内容。

## API 与后端变更

### 新的快速报告 API 界面

现有的面向对话的界面应被面向报告的界面取代。

建议的逻辑操作：

- 创建快速报告。
- 向报告追加章节。
- 按 ID 获取持久化报告。
- 获取报告章节负载。

精确的路由命名可以遵循现有的 API 惯例，但负载模型不应复用对话消息的 DTO。

### 生成服务

创建独立的快速报告生成路径，而非复用旧的对话响应契约。

生成器可以复用：

- AST 输出。
- 依赖图输出。
- 生成的 Wiki 数据。
- Mermaid 清理与渲染路径。

它还应引入快速报告专用的仓库分析索引，该索引在仓库索引期间持久化并在报告生成时复用。

初始实现不应要求 FAISS 索引或嵌入提供商来提供快速报告服务。

快速报告路径应发出专用的结构化报告 Schema 以及中间分析追踪。

### WebSocket 契约

快速报告 WebSocket 流应在最终章节负载可用之前支持中间分析事件。

建议的事件类型：

- `analysis_update`
- `section_complete`
- `report_complete`
- `error`

## 前端变更

### 替换 ChatPanel

当前的 `ChatPanel` 组件应被移除，并替换为快速报告工作区组件。

建议的 UI 拆分：

- `FastReportPage` 外壳
- `ReportStack`
- `ReportSection`
- `CitationLink`
- `EvidenceRail`
- `EvidenceBlock`

### FloatingAssistant 集成

`FloatingAssistant` 应继续将问题引导至快速报告流程。

该组件可能需要进行微小的模式更新，但应保持作为用户可见的问题入口点。

### 分析优先渲染

在章节完全生成之前，工作区应能渲染临时分析状态，显示：

- 当前分析阶段。
- 正在检查的文件列表。
- 每个文件在当前检索轮次中的角色。

章节完成后，此临时状态应被最终的 Markdown 章节和证据轨取代。

### 安全底部间距

页面外壳应测量渲染的 `FloatingAssistant` 高度，并将其暴露给滚动容器。

这可以通过以下方式实现：

- CSS 变量驱动的内边距 (Padding)。
- 已测量的占位元素 (Spacer)。
- 或共享的布局上下文 (Layout Context)。

实现方式灵活，但行为必须保持一致。

## 迁移与删除计划

一旦快速报告流程端到端工作正常：

- 移除现有的基于气泡的对话页面。
- 移除旧的底部对话输入框 (Composer)。
- 移除对话专用的流式 UI 契约。
- 移除废弃的前端状态和消息渲染路径。

流式生成内部可能仍然存在，但它应体现为报告章节生成状态，而非逐词显示的对话输出。

## 测试策略

### 前端

- 点击引用能够滚动到正确的证据块。
- 证据块高亮状态能正确更新。
- “扩展 +15”和“折叠”功能工作正常。
- 底部内容在 `FloatingAssistant` 上方保持可见。
- 持久化报告重新加载时无需网络生成调用。
- 活动章节能正确切换证据轨。

### 后端

- 报告生成持久化了预期的 Schema。
- TTL 过期得到强制执行。
- 报告重新加载不调用 LLM。
- Commit SHA 绑定得到保留。
- 在仲裁期间，无支撑的结论被降级或移除。
- 相关 Wiki 链接被确定性地附加。
- 检测到的中文问题产生中文报告输出，同时保留仓库原生代码标记。
- 快速报告生成不依赖 FAISS 的可用性。
- 分析追踪事件按确定性顺序持久化和流式传输。

### 端到端

- 从 `FloatingAssistant` 提交问题。
- 进入快速报告页面。
- 看到包含当前文件列表的分析状态。
- 看到最终的章节内容和同步证据。
- 在 TTL 内重新打开报告 URL 而不触发重新生成。
- 提出后续问题并看到追加的新章节。

## 风险

- 如果证据负载未严格绑定到 Commit SHA，可能会出现引用偏移。
- 如果生成规则过于宽松，可能会产生过多的 Mermaid 图表。
- 如果四个检索层未明确执行，可能会出现检索重叠。
- 如果证据扩展通过重复读取文件且不使用缓存来实现，可能会增加渲染复杂度。
- 如果未在移动端宽度下稳健测量 `FloatingAssistant` 的高度变化，可能会出现 UI 回退。
- 如果确定性的关键词和调用链扩展对于命名松散的代码库过于浅薄，可能会出现质量回退。
- 如果未在索引期间生成快速报告专用的仓库分析产物，可能会出现冷启动延迟。

## 验收标准

- 当前对话页面不再渲染基于气泡的对话 UI。
- `FloatingAssistant` 仍然是后续提问的入口。
- 每个问题产生一个结构化的报告章节，而非对话消息。
- 报告栈和证据轨通过引用 ID 保持同步。
- 所有引用的证据块按引用顺序显示在证据轨中。
- 证据块默认显示 `±3` 行，且每次点击可扩展 `15` 行。
- 页面底部内容在悬浮窗上方保持可见。
- 报告在唯一 URL 下持久化 7 天。
- 重新打开有效的报告 URL 不会触发新的 LLM 生成。
- 中文问题产生中文报告正文，不翻译仓库原生标识符。
- 快速报告不需要嵌入或向量搜索即可产生初始实现的结果。
- 最终结论基于代码证据或仓库结构证据。
- 相关 Wiki 内容作为扩展阅读显示，不作为主要证据。
- 工作区可以在渲染最终 Markdown 章节之前显示活动的分析文件列表。
- 遗留的对话 UI 代码路径可以安全移除。
