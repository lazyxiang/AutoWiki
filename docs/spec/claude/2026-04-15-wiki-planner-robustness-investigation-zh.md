# 根因调查：Wiki 规划器的鲁棒性

我将规划器损坏的输出结果与 `worker/pipeline/wiki_planner.py`、`ast_analysis.py` 以及 `dependency_graph.py` 进行了交叉比对。调查发现，有三种不同的失败模式导致了你所描述的症状，而其中只有一种是表面上看起来的那样。

## 发现 #1 —— 文件分配并非 LLM 的输出，而是字母顺序的轮询回退。

仔细观察每个页面接收到的文件。将规划器输出中的所有文件按字母顺序排序，并以 26（页面数量）为步长进行跨度分析：

| 步长索引 | 文件（按字母顺序） | 分配的页面 |
| :--- | :--- | :--- |
| 0 | .github/workflows/backend-ci.yml | AutoWiki Overview (第 0 页) |
| 1 | .github/workflows/frontend-ci.yml | Core Architecture and Design (第 1 页) |
| 2 | .pre-commit-config.yaml | System Configuration (第 2 页) |
| 3 | CLAUDE.md | Data Persistence and Models (第 3 页) |
| 4 | GEMINI.md | Global Logging and Telemetry (第 4 页) |
| 5 | README.md | The Ingestion Pipeline (第 5 页) |
| 6 | api/__init__.py | Code Analysis with Tree-Sitter (第 6 页) |
| … | | |

每个页面恰好包含 7 个文件，每个文件都是按字母顺序排列的下一个文件，偏移量为 `n*26 + page_index`。这种模式是由一段代码产生的 —— 即 `worker/pipeline/wiki_planner.py:654-659` 中的静默回退逻辑：

```python
# 回退方案：轮询分配（忽略验证约束）
result = {p["title"]: [] for p in outline}
titles = [p["title"] for p in outline]
for i, f in enumerate(sorted(all_files)):
    result[titles[i % len(titles)]].append(f)
return result
```

LLM 的阶段 2 文件分配调用在 3 次重试中全部失败，于是轮询回退产出了你所看到的结果。这种分配从来都不是 LLM 的判断 —— 而是 `sorted()` 取模 26 的结果。这就是为什么 `worker/pipeline/wiki_planner.py` 最终出现在“测试与验证”页面而不是“Wiki 规划与策略”页面的原因：第 25 页恰好根据字母顺序接收到了 `worker/pipeline/wiki_planner.py`，仅此而已。

### 为什么阶段 2 会静默失败

原因有多个，且相互叠加：

1. **输出基数巨大。** 在处理约 182 个文件时，LLM 必须在单个结构化响应中生成 182 个 `{file, page_title}` 对象。在这种规模下，受 Schema 约束的生成非常脆弱 —— 当 JSON 数组超过约 100 项时，Anthropic、OpenAI 和 Gemini 的性能都会下降，特别是当每项都引用一个必须与枚举精确匹配的自由格式字符串（`page_title`）时。
2. **缺乏部分成功处理机制。** `_assign_files` (`worker/pipeline/wiki_planner.py:619-652`) 将每次重试都视为“全有或全无”。如果 LLM 返回了 182 个有效分配中的 170 个，剩下的 12 个未分配文件不会触发任何操作；但如果验证因任何原因失败，整个响应就会被抛弃，并在提示词中追加“上一次尝试失败：……” —— 这通常会导致下一次尝试变得更糟，因为提示词增长了，但底层的处理难度并未改变。
3. **`_validate_assignments` 过于宽松，无法检测出错误的分配，但又过于严格，无法接受正确的分配。** 它只强制要求每页 ≤25 个文件且“非概览页面必须有 ≥1 个文件” (`wiki_planner.py:506-519`)。轮询分配满足这两个条件；与此同时，如果 LLM 做出了一个完全合理的分配，但导致“提供商实现”页面为空（因为 LLM 选择了“LLM 基础设施”页面），该分配就会被拒绝并重试。
4. **回退逻辑静默执行。** `_assign_files` 返回轮询结果，外层的 `generate_wiki_plan` 对其重新运行 `validate_wiki_plan` —— 但 `validate_wiki_plan` 也只检查结构约束，因此错误的数据通过了第二道关卡。没有任何 `logger.warning` 来区分“这是 LLM 生成的”还是“这是回退生成的”。用户看到的是一个损坏的 Wiki，且在日志中找不到任何 LLM 已放弃尝试的信号。

## 发现 #2 —— 大纲使流水线碎片化，因为提示词没有编码“架构局部性”。

阶段 1 的大纲生成 (`_build_outline_prompt`, `wiki_planner.py:327-392`) 告诉 LLM：

> ▎ 按语义目的分组，而非目录结构  
> ▎ 为大型仓库创建 2-3 层的层次结构  
> ▎ 页面标题应描述概念/组件，而非目录名称

这是一种缺乏制衡的“反目录”表述。结合依赖图信号（该信号将文件呈现为按计数排序的扁平边列表），LLM 捕捉到了局部聚类，但丢失了宏观架构：它看到“RAG 索引器导入 Embedding 提供商”，于是生成了“检索增强生成 (RAG)”作为一级页面，却忽略了 RAG 只是某个流水线的一个阶段这一事实。同样的情况也发生在“摄取流水线 (Ingestion Pipeline)”和“生成引擎 (Generation Engine)”上 —— 它们变成了平级的一级页面，而实际上它们应该是“生成流水线”页面下的兄弟页面。

提示词导致这一结果的三个具体原因：

1. **没有将架构锚点传递给阶段 1。** 虽然提供了 README，但 `worker/pipeline/__init__.py`、目录树以及包级 docstring（通常包含权威的架构描述）并未作为明显的信号呈现。
2. **聚类信号被降权。** `_build_outline_prompt` 仅包含 ≤20 个文件的聚类，且仅包含前 30 个。对于像 `worker/pipeline/` 这样属于一个大型强连通分量的仓库，这个在架构上起决定性作用的聚类会被抑制为“大型聚类 —— 请参阅上方的依赖关系”，导致 LLM 永远看不到“这 8 个文件构成了一个连贯的单元”。
3. **目录路径存在但未被强调。** `file_summary` 的每一行都以路径开头（如 `worker/pipeline/wiki_planner.py`），因此 LLM 可以看到目录分组，但提示词主动阻止其使用这一信息。指令应该是“将目录作为提示，仅在语义不一致时进行覆盖” —— 而不是“忽略目录”。

## 发现 #3 —— “一文件对应一页面”的约束被硬编码在三个地方，而不仅仅是一个。

你关于允许冗余分配将提高页面准确性的看法是正确的。该约束在以下位置被强制执行：

1. **Schema** —— `_ASSIGNMENT_SCHEMA` (`wiki_planner.py:283-299`) 使用了单数形式的 `page_title: string`，因此 LLM 甚至无法表达多页面分配。
2. **验证器去重** —— `_assign_files` (`wiki_planner.py:632-640`) 维护了一个 `assigned_files: set[str]`，并静默丢弃第一次之后的所有分配。即使 Schema 允许标题列表，这段代码也会丢弃重复项。
3. **刷新逻辑** —— `ingestion.py:418-424` 中的 `get_affected_pages` 已经通过迭代页面并检查成员身份来实现，因此它能正确处理出现在多个页面中的文件 —— 但 `wiki_plan.json` 中的存储方式是每页一个 `files: list`，这意味着多页面分配的文件在 JSON 中会有物理上的重复。这没问题，但值得明确指出。

页面生成器本身 (`page_generator.py:322-328`、`summarize_page_deps`、`_append_source_files_table`) 只读取 `spec.files`。它不假设页面之间具有唯一性。因此，下游已经是兼容的 —— 只有规划器在强制执行该约束。

# 全面解决方案

我建议分三个层次进行修复，按优先级排序：首先捕捉静默回退，然后确保分配阶段真正成功，最后改进大纲并允许受控的冗余。

## 层次 A — 停止静默失败（最高优先级，最小改动）

**目标：** 绝不再将轮询输出作为规划结果交付。

1. **让回退显式化。** 在 `_assign_files` 中，当所有重试都耗尽时，记录一个 ERROR 级别日志（而不是静默返回），包含失败的提示词末尾、最后一次尝试的验证错误以及文件/页面计数。为返回的规划标记一个 `degraded: True` 标志，以便可观测性系统能发现它。
2. **在 Worker 流水线中呈现降级后的规划。** 将 `plan_quality` 字段串联至 `WikiPlan` → 任务状态 → API。前端可以显示一个琥珀色横幅（“Wiki 结构是由回退启发式算法生成的 —— 请重新运行索引或通过 .autowiki/wiki.json 手动引导”）。
3. **用合理的方案替换轮询回退。** 轮询是最糟糕的分配方式，因为它主动破坏了目录局部性。使用基于目录聚类的回退方案代替它：按顶级目录段对文件进行分组，然后按二级目录段分组，再将每个聚类分配给最匹配的页面标题（通过标题与目录名的字符串相似度计算）。对于没有明显匹配的文件，分配给“Overview”而不是随机散布。这在 LLM 失败时提供了一个确定的、在语义上可辩护的回退方案。
4. **事后检测轮询形状的输出。** 在 `validate_wiki_plan` 中增加一个启发式检查：如果每个页面的文件数恰好相同（误差 ±1），或者页面大小的标准差接近于零且文件在各页面间按字母顺序交错，则抛出 `ValueError("分配结果看起来像轮询回退")`。这会强制外层循环进入上述新的目录聚类回退流程。

仅这四项改动就能捕捉到你观察到的 bug。甚至在进行任何规划器质量提升工作之前，你就能在日志中看到错误，并看到一个降级质量横幅，而不是一个看起来没问题但无法使用的 Wiki。

## 层次 B — 使阶段 2 真正成功（中等工作量，最大质量提升）

**目标：** LLM 的分配尝试应该是收敛的，而不是崩塌的。

1. **对分配任务进行分块。** 将 `all_files` 分成约 40 个文件一组的批次。对于每个批次，调用 LLM，并提供完整的大纲、该批次文件以及要求其仅分配这些文件的提示词。合并结果。这解决了基数问题：每次调用产出的 JSON 对象 ≤40 个，完全在可靠的结构化输出范围内。通过 `LLMProvider.generate_batch`（根据 `CLAUDE.md`，该功能已存在）并行运行各批次。
2. **随大纲传递每页的锚点。** 在构建分配提示词时，除了大纲之外，为每个页面包含一两个“种子文件” —— 通过页面标题+目的与文件索引之间的字符串/导入相似度预先计算得出。例如，对于“Wiki 规划与策略”页面，种子文件将是 `worker/pipeline/wiki_planner.py` 和 `tests/worker/test_wiki_planner.py`，这是通过将页面标题的内容词与文件路径组件和模块 docstring 关键词进行匹配得出的。这为 LLM 提供了锚点，并极大地减少了偏离。
3. **允许部分响应。** 当 LLM 返回 M 个分配中的 N 个时，接受这 N 个并仅针对缺失的 M-N 个重新进行提示 —— 不要抛弃整个响应。这能将 100% 的重试转换为小规模的定向重试，从而更快收敛并产生更好的输出。
4. **在不破坏验证器的前提下加强它。** 用更智能的检查替换“每页 ≤25 个文件 / 非概览页面必须非空”：
    - 仅当超过 40% 的文件集中在单个页面时才拒绝（LLM 偷懒的迹象） —— 但仅在尝试过锚点 + 分块之后。
    - 当超过 20% 的页面为空时拒绝（大纲契合度差的迹象，这应该重试大纲生成，而不是分配过程）。
    - 当依赖图中的一个聚类散布在超过 3 个页面时发出警告（不拒绝）。
5. **对批次使用 `fast_llm`，仅在重试时升级到 `llm`。** 当前代码的做法相反 —— 先使用 `fast_llm` 然后升级。这是正确的；只需确保分块调用遵循这一模式即可。

## 层次 C — 大纲质量与多页面分配

**目标：** 大纲反映实际架构，且在有根据的情况下允许页面共享文件。

### C1. 更好的大纲锚点

1. **显式呈现目录树。** 在 `_build_outline_prompt` 中增加一个部分，打印前 3 层的目录树及其文件计数：
   ```text
   仓库结构 (前 3 层):
     api/         (8 个文件)
     api/routers/ (4 个文件)
     worker/      (12 个文件)
     worker/pipeline/ (15 个文件)   ← 最大的内部包
     ...
   ```
2. **以及随附的指令：** “最大的内部包通常是具有意义的架构单元。除非依赖分析另有说明，否则请将它们作为层级提示。”
3. **重新构思“反目录”规则。** 用“按语义目的分组。目录是一个强有力的默认信号 —— 仅在不同目录中的文件构成紧密的语义单元（例如前端组件及其后端路由）时，才覆盖目录结构”来替换“按语义目的分组，而非目录结构”。
4. **将大型聚类提升为一级信号。** 停止抑制超过 20 个文件的聚类。相反，用它们的包级模式来概括它们：“大型聚类：worker/pipeline/* (15 个文件) —— 极有可能是单个子系统；请考虑设立一个父页面，并按文件角色设立子页面。”
5. **传递包级 docstring。** 当 `worker/pipeline/__init__.py`、`api/__init__.py` 等包含模块 docstring 时，在“包描述”下将它们原封不动地包含在大纲提示词中。这些通常包含权威的架构说明，能引导 LLM 进行正确的分组。
6. **添加从 README 中提取的“子系统提示”。** 如果 README 包含诸如“核心组件”或“生成流水线”之类的标题，将它们提取为列表，并作为“作者声明的子系统”传递给提示词。

### C2. 多页面文件分配

1. **Schema 变更。** 更新 `_ASSIGNMENT_SCHEMA` 以允许每个文件的主要 + 次要分配：
   ```json
   {
     "file": "worker/pipeline/wiki_planner.py",
     "primary_page": "Wiki Planning and Strategy",
     "secondary_pages": ["Generation Pipeline", "LLM Infrastructure"]
   }
   ```
2. **将次要页面限制在 2 个以内以防止滥用。**
3. **提示词指令。** 告诉 LLM： “一个文件可以出现在最多 3 个页面中：它的主要归属地，以及最多 2 个由其提供必要支持上下文的页面。仅在省略该文件会导致次要页面被迫虚构或忽略关键细节时，才使用次要分配。” 这设定了一个高标准，防止 LLM 将文件随处散布。
4. **验证器变更。**
    - 丢弃 `_assign_files` 中 `assigned_files: set` 的去重逻辑。改为跟踪 `primary_assigned`，确保每个文件恰好有一个主要归属地。
    - 增加检查：每页的次要文件数 ≤ 主要文件数的 30%（防止页面充满借用的文件）。
    - 增加检查：任何作为次要文件出现在 N 个页面中的文件，会对依赖聚类连贯性警告贡献 N 次权重。
5. **存储。** `wiki_plan.json` 保持现有的每页 `files: list` —— 由主要 + 次要文件填充。增加一个单独的 `primary_files: list`，以便刷新逻辑能够区分“文件已更改 → 我是归属地”与“文件已更改 → 我只是借用它”，且只有归属地页面会触发全量重新生成。借用页面可以使用更快的重新生成路径，或者如果借用文件与该页面目的的相关性未发生变化，则跳过重新生成（这是 Phase-2 的优化）。
6. **对刷新的影响。** `get_affected_pages` 已经在迭代 `page.files` —— 如果一个文件出现在多个页面中，它将“开箱即用”。唯一的细微差别是增量刷新成本：现在编辑一个核心文件会使更多页面失效。可以通过将 `primary_files` 作为严格触发器，并将次要出现视为可选但非必须的重新生成来缓解这一问题。
7. **对页面生成器的影响。** `page_generator.py:322` 读取 `spec.files` 并提供实体 + 依赖摘要。已经兼容。阶段 2 的提示词应提到：“某些文件仅作为支持上下文出现在此页面中 —— 请将叙述重点放在本页面的主要主题上，而不是对借用的文件进行文档化。” 在 `page_draft.build_draft_prompt` 中添加此条件指令。

## 实施顺序建议

我建议按以下顺序实施这些方案，每个方案使用独立的分支：

1. **层次 A（捕捉失败）** —— 半天。止住目前的“流血”。如果没有这一步，你将无法判断后续的改进是否生效。
2. **层次 B（分块分配 + 锚点 + 部分接受）** —— 1–2 天。仅这一项就应该能修复用户报告的案例（通过锚点种子投放 + 更小的批次，`wiki_planner.py` 将落在“Wiki 规划与策略”页面）。
3. **层次 C1（大纲锚点）** —— 1 天。修复流水线碎片化问题；需要针对几个真实仓库进行评估以微调提示词。
4. **层次 C2（多页面分配）** —— 1–2 天。质量润色；紧迫性较低，因为修复主要分配质量（B + C1）已能恢复大部分丢失的准确性。多页面分配是针对长尾情况的优化。

## 在编写代码前需要验证的内容

在开始层次 B 之前，我想确认阶段 2 在该仓库上是否确实失败了（而不仅仅是看起来失败了）。一个快速检查的方法：使用 `LOG_LEVEL=DEBUG` 重新运行索引，并查找“上一次尝试失败：”行 —— 它们将揭示 LLM 是生成了无效的 JSON、丢失了文件，还是遇到了超时。修复方法各不相同：

- **无效 JSON** → 分块输出是解决方案 (层次 B1)。
- **丢失文件** → 部分接受重试 (层次 B3)。
- **超时 / Token 限制** → 两者结合，并考虑将分配阶段切换为流式调用，以增量方式发出分配结果。

考虑到在单个结构化响应中处理 182 个文件，我有强烈的预感“这三者正在同时发生”，但在编写 1,500 行重构代码之前进行调试运行确认可以避免返工。

---

**一句话总结：** 灾难性的输出是轮询回退的结果，而非 LLM 的判断。`wiki_planner.py:654-659` 中隐藏的静默失败路径掩盖了真实问题。首先修复可观测性 (层次 A)，然后通过分块 + 锚点 + 部分接受确保阶段 2 成功 (层次 B)，最后改进大纲锚定并增加受控的多页面分配 (层次 C)。分配质量问题和流水线碎片化问题是独立的根因，都需要各自的修复方案。
