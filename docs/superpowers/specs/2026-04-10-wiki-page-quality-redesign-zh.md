# Wiki 页面质量重新设计

**日期：** 2026-04-10
**状态：** 已实现并合并至 `main` 分支（PR #15 和 #17）
**范围：** 第 5 阶段（Wiki 规划器）和 第 6 阶段（页面生成器），以及对 LLM 提供商抽象层的横向扩展。

## 实现说明（与规格说明的偏差）

- **未接入 `cache_ttl: long`**：配置字段 `LLMConfig.cache_ttl` 接受 `"short" | "long"` 并默认为 `"short"`，但 Anthropic 提供商无论如何设置都会发出 `"ephemeral"`（临时）缓存控制。§8.3 中描述的 1 小时 TTL 路径未实现 —— `cache_ttl` 仅作为未来工作的占位符。
- **未添加 `llm.fact_check_model` 逃生舱**：§12 开放问题 1 提议了 `llm.fact_check_model: fast | main` 配置开关。该功能未实现；事实检查始终使用 `fast_llm`。

## 1. 目标

在不实质性增加成本的前提下，通过改变流水线生成每个页面的方式，提高生成的 Wiki 页面的准确性和质量。

重新设计的动力源于三个具体需求：

1. **源代码是权威的唯一事实来源。** 非 README 的设计文档（如 `ARCHITECTURE.md`、`DESIGN.md` 等）可能会随着项目的迭代而过时。页面生成必须优先选择源代码而非这些文档，并将任何文档内容视为 *提示* 而非事实。
2. **Wiki 输出中不得包含原始代码片段。** 页面不应嵌入带围栏的源码块，而应使用正文、项目列表、表格和图表 *综合* 描述代码的功能。
3. **更丰富的图表种类。** 将图表范围从流程图和类图扩展到涵盖完整的 Mermaid 调色板 —— 序列图、状态图、ER 图、旅程图、甘特图、思维导图 —— 并要求每个图表都带有简短的标题和源码引用。

在集思广益过程中浮现了第四个隐性目标：**提高针对幻觉的接地性（grounding）。** 即使输入完美，LLM 也会捏造方法名称、误读控制流并混淆相似的函数。验证环节可以捕捉这类错误。

## 2. 非目标

- 不更改摄取、AST 分析、依赖图或 RAG 索引器阶段（第 1-4 阶段），但会更改检索时对文档文件的 *评分* 方式。
- 不更改 Wiki 页面的前端渲染。
- 不引入新的 LLM 提供商。本设计扩展了现有的提供商（Anthropic、OpenAI、Gemini、Ollama、OpenAI 兼容）。
- 不提供向后兼容的“单阶段模式” —— 多阶段流程将完全取代当前的单阶段生成器。

## 3. 高层形态

### 3.1 每页生成流程（取代单阶段）

```text
大纲 (快速模型)
  → 草稿 (主模型)
    → 事实检查 (快速模型)
      → 修订 (主模型，有条件触发) — 仅针对性修复
```

所有四个阶段共享缓存的每页证据上下文，以保持成本持平。

### 3.2 支持性变更

- **检索层**：文档文件被降权并设置上限；页面生成器提示词被告知文档可能过时，代码才是权威来源。
- **LLM 提供商接口**：扩展了支持缓存标记的 `PromptSegment` 抽象。每个提供商将其转换为其原生的缓存原语（或忽略它们）。
- **快速模型分离**：新增 `llm.fast_model` 配置选项，表现为第二个 `LLMProvider` 实例 (`fast_llm`)。如果未设置，则默认为主模型。
- **规划器**：第 2 阶段（文件分配）移至快速模型。第 1 阶段（大纲）保留在主模型上。
- **父页面流程**：改为使用子页面 Markdown + 依赖图作为主要证据，而非源码块。

## 4. 检索层变更

### 4.1 文档降权

目前的 RAG 索引器在检索时将 `.md`、`.rst`、`.txt` 和 `.adoc` 文件与源代码同等对待。这导致如果页面的关键词刚好与文档标题匹配，过时的设计文档就会主导检索到的上下文。

**变更**：`FAISSStore.search()` 和 `FAISSStore.multi_search()` 获得一个可选参数，将结果划分为“代码”和“文档”两个桶，并应用独立的上限。

```python
store.multi_search(
    query_vecs,
    k=12,
    doc_k=1,         # 最多 1 个文档分块；代码获得 k - doc_k 个槽位
)
```

- 页面生成器的 `doc_k` 默认为 1。
- 代码分块数量推导为 `k - doc_k`（不是独立参数）。
- README 摘录 *不* 通过 RAG 路径检索 —— 规划器已经直接使用了 README，页面生成器不需要它。
- 分类使用文件扩展名：`{".md", ".rst", ".txt", ".adoc"}` → 文档；其他所有文件 → 代码。（与 `rag_indexer.is_code_file()` 保持一致。）

### 4.2 提示词层级指令

页面生成器 `_SYSTEM` 提示词获得了一条明确的优先级规则：

> **事实来源**：下面提供的源代码是权威的。任何文档摘录（以 `.md`、`.rst` 等结尾的文件）都可能已经过时，必须视为 *提示* 而非事实。当文档与代码不一致时，请信任代码。切勿引用文档文件作为技术断言的来源 —— 请引用实际实现该行为的代码文件。

这是必要的防线：即使过时的文档分块混入检索结果，模型也会将其视为不可信。

## 5. 多阶段页面生成

### 5.1 第 1 阶段 — 大纲（快速模型）

**目的**：在编写任何正文之前，为页面生成结构化计划。该计划既能 *引导草稿编写*，又能 *作为事实检查阶段的目标*。

**输入**（约 2–3k token，可缓存的实体摘要）：
- 页面标题、目的、父页面（如果有）
- 分配文件的实体摘要（类型、名称、签名、单行文档摘录）
- 依赖信息：`depends_on`、`depended_by`、`external_deps`
- 带有单行摘要的文件列表
- （针对父页面）子页面的标题和目的
- 输出架构 (Schema)

**输出** (JSON)：

```json
{
  "sections": [
    {
      "heading": "Overview",
      "kind": "prose",
      "focus": "What the RAG Indexer does and why it exists",
      "diagram": null
    },
    {
      "heading": "Chunking Strategy",
      "kind": "prose+table",
      "focus": "Token limits, overlap, language-specific splitters",
      "diagram": {
        "type": "flowchart",
        "purpose": "Show the chunking pipeline from raw file to FAISS vector",
        "source_files": ["worker/pipeline/rag_indexer.py"]
      }
    },
    {
      "heading": "Query Flow",
      "kind": "prose",
      "focus": "Multi-query RAG retrieval sequence",
      "diagram": {
        "type": "sequenceDiagram",
        "purpose": "Outline → query embedding → FAISS search → dedup → return",
        "source_files": ["worker/pipeline/page_generator.py"]
      }
    }
  ],
  "key_claims": [
    "FAISSStore uses IndexFlatIP for cosine similarity",
    "multi_search() deduplicates chunks across queries by (file, start_line)",
    "Chunk size defaults to 1000 characters with 200-character overlap"
  ]
}
```

由校验逻辑强制执行的 **架构规则**：
- `kind` 是 `prose`、`prose+table`、`prose+list`、`prose+diagram`、`prose+table+diagram` 之一。
- `diagram.type` 是扩展后的 Mermaid 调色板 (§5.5) 之一。
- `diagram.source_files` 必须是分配给该页面的文件的子集。
- 每个页面必须生成至少 1 个图表；具有 ≥ 3 个小节的页面必须生成至少 2 个图表。
- `key_claims` 必须包含 3–8 项。每项断言必须引用可以针对源代码进行验证的内容（不得包含类似“设计很优雅”之类的模糊陈述）。

校验失败会在大纲阶段内部自动重试最多 2 次，镜像了规划器现有的重试模式。

### 5.2 第 2 阶段 — 草稿（主模型）

**目的**：根据大纲生成完整的 Markdown 页面。

**输入**（约 8k token 已缓存的检索源码分块；可变末尾约 1k token）：
- **已缓存前缀**：系统提示词、仓库级上下文、每页源码分块 (`code_k=11`, `doc_k=1`)、实体详情、依赖信息
- **可变末尾**：大纲 JSON、草稿撰写说明、正文/图表要求

**提示词中的正文规则**：
- 切勿嵌入带围栏的代码块（既不准使用 ` ```python` 也不准使用 ` ```js`）。唯一允许的围栏块是 ` ```mermaid`。
- 允许使用简短的行内标识符，如 `ClassName.method()` 或 `MAX_RETRIES = 3` —— 这些描述了 API 表面，而非代码摘录。
- 每个主要断言后都必须附带现有的斜体格式源码引用：`*Source: worker/pipeline/rag_indexer.py:120-145*`
- 优先使用表格和项目列表来枚举选项、字段、参数或对比。优先使用正文进行叙述和阐述设计原理。
- 发出的每个图表必须与大纲中的相应条目匹配。图表前必须有一个加粗的单行标题，后接一行源码引用。

图表标题/源码格式：

````markdown
**Diagram: Query flow through multi-query RAG**

```mermaid
sequenceDiagram
    ...
```

*Source: worker/pipeline/page_generator.py:403-517*
````

### 5.3 第 3 阶段 — 事实检查（快速模型）

**目的**：针对源代码验证大纲中的 `key_claims`（关键断言），并检查每个图表断言的关系在代码/依赖图中是否存在。

**输入**（重用快速模型的实体摘要缓存；可变末尾携带草稿和目标分块）：
- **已缓存前缀（快速模型）**：实体摘要 + 依赖信息（约 2k token，与大纲阶段相同的缓存）
- **可变末尾**：草稿 Markdown、`key_claims` 列表、每个断言的目标源码分块片段，以及每个图表引用的源码文件列表以及父页面图表的依赖图边

**输出** (JSON)：

```json
{
  "verdict": "fail",
  "issues": [
    {
      "kind": "claim",
      "claim": "FAISSStore uses IndexFlatL2 for Euclidean distance",
      "section": "## Chunking Strategy",
      "reason": "Source shows IndexFlatIP (inner product), not L2. See rag_indexer.py:78",
      "suggested_fix": "Replace IndexFlatL2 with IndexFlatIP and update the 'Euclidean distance' phrasing"
    },
    {
      "kind": "diagram",
      "diagram_index": 1,
      "section": "## Query Flow",
      "reason": "Sequence diagram shows arrow from FAISSStore → EmbeddingProvider; no such call exists. Embedding happens before the FAISSStore.search() call.",
      "suggested_fix": "Reverse the arrow: move the embedding step before the FAISSStore interaction"
    }
  ]
}
```

**结论 (Verdict) 取值**：`pass`、`fail`。如果为 `pass`，页面将立即发布。

**事实检查不做的事情**：
- 它不会重新验证草稿中的所有内容 —— 仅验证 `key_claims` 列表和声明的图表。这就是事实检查能在快速模型上廉价运行的原因。
- 它不会重写草稿。它的唯一工作是生成结构化的问列表。

### 5.4 第 4 阶段 — 针对性修订（主模型，有条件触发）

仅在 `verdict == "fail"` 时运行。每页最多尝试一次修订。

**行为**：

- **正文断言问题**：一个新的主模型 LLM 调用接收 `(草稿 + 问题列表 + 相关源码分块)`，指令是仅修订包含标记断言的小节，并保持其他所有小节 **原封不动**。重用草稿阶段的缓存前缀。
- **图表问题**：根据 (`section` + `diagram_index`) 定位具体的 ```mermaid 块，并将其发送给主模型，附带 `(小节标题 + 计划的图表类型 + 事实检查问题 + 相关源码分块 或 父页面的依赖图边)`。模型仅返回修正后的 mermaid 块。我们将其拼接回草稿中并重新运行 `sanitize_mermaid_blocks()`。
- **混合问题**：先进行正文修订，然后进行逐个图表的重新生成。

**如果持续失败**（修订后事实检查仍报告问题）：
- 记录一条警告，并将剩余问题附加到任务记录中。
- **针对断言**：通过将 `claim` 字符串与草稿文本进行匹配（子串匹配，不区分大小写）来定位标记的句子。如果匹配成功，将包含该句子的部分替换为 `<!-- removed: reason -->`。如果不匹配（例如修订时改写了它），记录一条警告并按原样发布草稿 —— 模糊的断言总比静默删除错误的文本要好。发布页面。
- **针对图表**：完全丢弃 mermaid 块，并替换为 `<!-- diagram removed: reason -->`。发布页面。

这防止了无限重试循环。同时也保证了我们永远不会发布已知错误的图表或断言 —— 我们宁愿留白也不愿撒谎。

### 5.5 扩展的 Mermaid 调色板

页面生成器提示词列出了完整的支持集，并给出了何时选择每种图表的明确指导：

| 图表类型 | 用于 |
|---|---|
| `flowchart TD` / `flowchart LR` | 流水线阶段、数据流、决策树 |
| `sequenceDiagram` | 请求/响应流、协议交换、组件间消息排序 |
| `classDiagram` | 类层次结构、继承、组合关系 |
| `stateDiagram-v2` | 有限状态机、任务生命周期、连接状态 |
| `erDiagram` | 数据库架构、记录关系（例如 `repositories` ↔ `jobs` ↔ `wiki_pages`） |
| `journey` | 面向用户的端到端工作流演练（例如“索引一个仓库”） |
| `gantt` | 时间阶段或发布计划 —— 极少适用；仅用于描述预定/阶段性工作的页面 |
| `mindmap` | 概念概述、子系统分类 —— 对父页面非常有用 |
| `graph LR` | 依赖关系、导入图 |

提示词指示模型选择那些 *能传达正文无法简洁表达的信息* 的图表，而不是为了添加图表而添加。大纲校验规则 (§5.1) 设置了最小数量以防止图表稀缺；本规则设置了质量标准以防止干扰。

### 5.6 标题和源码引用格式（强制执行）

生成的页面中的每个图表块必须遵循以下确切结构，由一个轻量级后处理器进行检查：

````markdown
**Diagram: <单行标题>**

```mermaid
<body>
```

*Source: <file_path>:<start_line>-<end_line>*
````

如果后处理器发现 mermaid 块缺少前置标题行或后置源码行，它会插入一个占位标题（“Diagram”）和一个根据大纲的 `source_files` 推导出的尽力而为的源码引用。（这是一个安全网 —— 提示词才是主要机制。）

## 6. 父页面流程

父页面（具有子页面的页面，自底向上处理）遵循相同的 4 阶段结构，但有三点不同。

### 6.1 证据组合

父页面 **不** 使用 RAG 检索作为其主要证据来源。它们的上下文是：

- 它们 **已通过事实检查** 的子页面的 Markdown（来自当前运行）
- 子页面文件之间的 **依赖图边**
- 针对高层入口点（顶级 `main` 函数、公共服务初始化程序）的一小部分源码分块 —— 通过针对性查询检索

子页面 Markdown 是可信内容：每个子页面都已经通过了自身的事实检查。父页面是一项综合任务，而非提取任务。

### 6.2 大纲和事实检查目标

- 父页面 **大纲** 由子页面标题塑造 —— 小节通常描述子页面如何组合在一起，而不是每个子页面具体做了什么。
- 父页面 **事实检查** 区分三种断言类型：
  - **子页面衍生断言**（父页面重述了子页面已经说过的内容）：可信，跳过事实检查。
  - **架构断言**（例如“规划器调用 RAG 索引器”）：针对 **依赖图** 进行验证，而非源码分块。确定性的图查找，不需要为此调用 LLM。
  - **新颖断言**（父页面断言的其他任何内容）：与叶子页面相同，针对源码分块进行验证。

这使得父页面的事实检查比叶子页面的事实检查便宜得多。

### 6.3 父页面图表

父页面图表往往跨越多个组件 —— 跨组件流的序列图、子系统结构的思维导图、高层数据流的流程图。当其中一个未通过事实检查时，重新生成提示词会将依赖图边作为事实来源（而非源码分块），因为关于“组件 A 是否调用组件 B”的真相存在于图中。

## 7. 规划器变更

### 7.1 第 2 阶段移至快速模型

现有的两阶段规划器根据认知负荷进行了清晰划分：

- **第 1 阶段 — 大纲**（标题、目的、父级层次结构）是创造性综合。保留在主模型上。
- **第 2 阶段 — 文件分配**（每个文件 → 一个页面）是分类。移至快速模型。

校验已经能捕捉到内容过满或空的页面，因此快速模型较低的创造力不是风险。如果快速模型在“带反馈重试”时表现不佳，我们仅在第二次重试时升级到主模型（可配置的回退方案）。

### 7.2 第 1 阶段和第 2 阶段之间的缓存重用

第 1 阶段和第 2 阶段共享相同的大量输入：`file_summary`、`dep_info`、`clusters`。目前这些内容被重新构建成两个独立的提示词。在新的 `PromptSegment` 接口下，两个阶段都将这些共享输入标记为可缓存前缀。可变末尾在第 1 阶段的大纲架构和第 2 阶段的分配架构之间切换。

**注意**：第 1 阶段在主模型上运行，第 2 阶段在快速模型上运行，因此缓存前缀是独立写入每个模型的缓存中的 (§8.5)。节省来自 *阶段内* 重试的重用（例如，当第 1 阶段自动重试时，重试会命中缓存前缀）以及 *第 2 阶段使用快速模型*（无论是否缓存，其成本都更低）。

## 8. LLM 提供商接口扩展

### 8.1 `PromptSegment` 抽象

```python
from dataclasses import dataclass

@dataclass
class PromptSegment:
    text: str
    cacheable: bool = False
```

每个 `LLMProvider` 方法都获得一个重载，接受 `list[PromptSegment]` 代替 `str`：

```python
async def generate(
    self,
    prompt: str | list[PromptSegment],
    system: str | list[PromptSegment] = "",
) -> str: ...
```

传递纯字符串相当于传递 `[PromptSegment(text=..., cacheable=False)]`。这使得不关心缓存的调用点保持不变。

### 8.2 逐个提供商的转换

| 提供商 | 行为 |
|---|---|
| **Anthropic** | 分段变成内容块。`cache_control: {"type": "ephemeral"}` 被附加到每个连续运行中的最后一个可缓存分段上（最多达到 Anthropic 的 4 个断点限制）。系统分段同样通过结构化的 `system` 参数进行标记。 |
| **OpenAI** | 忽略标记。OpenAI 根据请求前缀应用自动前缀缓存（50% 折扣）；将稳定内容排在前面就足够了。提供商的工作是按顺序连接分段且不打乱顺序。 |
| **OpenAI 兼容** | 与 OpenAI 相同。实际节省取决于后端是否实现了前缀缓存；视为尽力而为。 |
| **Gemini** | 初始实现中仅采用隐式缓存：按顺序连接分段，并依赖 Gemini 2.5 的自动前缀检测（Flash 需要 ≥ 1k token，Pro 需要 ≥ 4k）。显式 `cachedContents` 是后续工作，取决于测量的需求，因为 Gemini 有每小时存储费用和生命周期管理成本。 |
| **Ollama / 本地** | 忽略标记。无缓存，无成本。 |

### 8.3 缓存 TTL 配置

一个新的配置开关 `llm.cache_ttl`：

```yaml
llm:
  cache_ttl: short  # "short" (默认, 5 分钟 TTL) 或 "long" (1 小时 TTL)
```

- `short` 使用 Anthropic 默认的临时缓存（5 分钟，1.25 倍写入成本）。
- `long` 使用 Anthropic 的 1 小时缓存（2 倍写入成本）。旨在用于页面生成批次跨越多个 5 分钟窗口的超大型仓库。
- 被所有非 Anthropic 提供商忽略。

### 8.4 快速模型配置

```yaml
llm:
  provider: anthropic
  model: claude-sonnet-4-6        # 现有 — 主模型 / 质量模型
  fast_model: claude-haiku-4-5    # 新增 — 分类 / 验证模型
```

环境变量：`AUTOWIKI_LLM_FAST_MODEL`。如果未设置，则默认为 `llm.model` 的值（对于不想进行模型分离的用户无影响）。

在 Worker 启动时，工厂构建 **两个 `LLMProvider` 实例**：`llm`（主模型）和 `fast_llm`（快速模型）。两者都与现有的 `embedding` 依赖项一起贯穿整个流水线。当 `fast_model == model` 时，工厂返回 *同一个* 实例两次 —— 无重复。

### 8.5 跨模型缓存行为（显式说明）

缓存以 `(model_id + prefix_content + params)` 为键。主模型写入的缓存不能被快速模型读取，反之亦然。因此，多阶段流程每页会写入 *两个* 缓存：

- **主模型缓存** — 完整源码分块（约 8k token），在草稿阶段写入一次，在修订阶段读取。
- **快速模型缓存** — 实体摘要 + 依赖信息（约 2k token），在大纲阶段写入一次，在事实检查阶段读取。

这是一个深思熟虑的设计选择：快速阶段不需要完整的分块，因此我们向快速模型缓存写入一个较小的前缀，而不是复制 8k 的分块前缀。参见 §9 的成本影响。

## 9. 成本和延迟分析

### 9.1 每页成本 (Anthropic Sonnet + Haiku)

假设：每页约 8k token 源码分块，约 2k token 实体摘要，修订触发概率约 30%。定价：Sonnet $3/M 输入，$15/M 输出；Haiku $1/M 输入，$5/M 输出。缓存输入 $0.30/M (Sonnet) / $0.10/M (Haiku)；缓存写入为正常的 1.25 倍。

| 阶段 | 模型 | 输入 (缓存) | 输入 (可变) | 输出 | 估算成本 |
|---|---|---|---|---|---|
| 大纲 | Haiku | 2k (写入, 首阶段) | 1k | 0.8k | ~约 $0.004 |
| 草稿 | Sonnet | 8k (写入, 首阶段) | 1k | 2k | ~约 $0.038 |
| 事实检查 | Haiku | 2k (读取, 已缓存) | 3k 草稿 + 分块 | 0.5k | ~约 $0.008 |
| 修订 (~30%) | Sonnet | 8k (读取, 已缓存) | 2k 草稿 + 问题 | 1.5k | ~平均 $0.010 |
| **总计** | | | | | **~约 $0.060/页** |

当前单阶段成本：~约 $0.060/页。**净变化：基本持平。** 快速模型的分离和提示词缓存抵消了额外的阶段支出。

### 9.2 每个仓库的成本

| 仓库大小 | 当前 | 新版 | 变化 |
|---|---|---|---|
| 小型 (10 页) | ~约 $0.60 | ~约 $0.60 | ~约 $0 |
| 中型 (25 页) | ~约 $1.50 | ~约 $1.50 | ~约 $0 |
| 大型 (60 页) | ~约 $3.60 | ~约 $3.60 | ~约 $0 |

得益于快速模型上的第 2 阶段以及缓存重用，大型仓库的规划器成本下降了约 25%。

### 9.3 延迟

每页：关键路径上有约 3 个连续的 LLM 往返（大纲 → 草稿 → 事实检查），修订会为约 30% 的页面增加第 4 个。每页的墙钟时间大约是 **当前单阶段的 2–2.5 倍**，但相同深度的页面仍然并行批处理，因此整体任务延迟的增长比单页延迟更平缓。

### 9.4 无丰富缓存功能的提供商

- **OpenAI / OpenAI 兼容**：自动前缀缓存，提供 50% 折扣。成本约为当前的 1.3 倍。
- **Gemini 2.5 (隐式缓存)**：符合条件的前缀约有 75% 折扣。成本约为当前的 1.1–1.2 倍。
- **Gemini 1.5**：无隐式缓存。成本约为当前的 2.5 倍 —— 应鼓励用户升级或更换。
- **Ollama / 本地**：无外部成本。延迟影响（约 3 倍往返）是唯一的担忧；本地推理每次调用的速度较慢。

## 10. 迁移

不提供向后兼容性。`worker/pipeline/page_generator.py` 中单阶段的 `generate_page` 和 `generate_page_batch` 被四阶段流水线取代。`worker/jobs.py` 中的单阶段调用者已更新，以同时传递 `llm` 和 `fast_llm`。

被破坏的接口表面：

- `LLMProvider.generate()` 签名接受 `str | list[PromptSegment]`。内部调用者已更新；无公共 API 变更（LLMProvider 未在 Worker 外部公开）。
- `worker/jobs.py` 工厂在 Worker 启动时构建两个提供商实例。配置加载获得 `llm.fast_model` 和 `llm.cache_ttl`。
- 第 6 阶段编排逻辑（`worker/jobs.py` 中的 `run_full_index` 和 `run_incremental_refresh`）更改为调用四阶段生成器。

增量刷新流程不受影响，除了刷新的页面会像全量索引页面一样经过相同的四阶段生成器。

## 11. 测试策略

### 11.1 单元测试

- 每个提供商的 `PromptSegment` 转换（Anthropic、OpenAI、Gemini、Ollama） —— 验证顺序是否正确以及缓存标记位置是否正确（仅限 Anthropic）。
- 大纲架构校验 —— 重复章节、多章节页面缺少图表、无效图表类型。
- 事实检查问题解析和图表块拼接 —— 给定草稿和结构化问题列表，拼接器生成预期的修订后草稿。
- `FAISSStore.multi_search` 中的文档降权 —— 混合代码/文档语料库，验证是否遵守 `doc_k` 上限且代码分块计数等于 `k - doc_k`。
- 标题/源码引用后处理器 —— 验证它仅在缺失时插入占位符，并保持符合规范的块不动。

### 11.2 集成测试

- 使用现有的 `mock_llm` 和 `mock_embedding` 固件，针对 `tests/fixtures/simple-repo/` 处的固件仓库端到端运行四阶段流水线。
- 模拟事实检查阶段返回 `pass` 和 `fail` 结论；验证修订仅在 `fail` 时触发。
- 模拟事实检查在修订后仍然失败；验证确定性的“剥离并发布”回退方案。
- 父页面流程：使用故意划分父/子的固件；验证父页面使用子页面 Markdown 而非源码分块，并且经依赖图验证的架构断言绕过了 LLM 事实检查。

### 11.3 覆盖率目标

保持 `worker/` 现有的 80% 目标。新模块（多阶段编排器、事实检查、修订拼接器）应达到 ≥ 85%，因为它们是没有任何历史包袱的新代码。

## 12. 开放问题 / 风险

1. **快速模型在事实检查上的质量**。如果 Haiku 系统性地忽略了细微的幻觉，事实检查就会变成一个产生虚假安全感的层。缓解措施：提供一个配置逃生舱 (`llm.fact_check_model: fast | main`)，以便用户在观察到问题时强制将事实检查移至主模型。默认保持为 `fast`。
2. **Gemini 1.5 用户支付 2.5 倍费用**。已记录，但值得在发布说明和 README 中明确说明。
3. **缓存 TTL 与超大型仓库**。一个拥有 100+ 页面的仓库在每个深度级别可能会跨越多个 5 分钟窗口，导致批处理中途缓存失效。`llm.cache_ttl: long` 开关是逃生舱，但默认值为 `short`。如果测量显示默认值对典型的 AutoWiki 用户不合适，我们就翻转默认值。
4. **图表最小限制可能会在小页面上产生被迫生成的图表**。大纲规则“具有 ≥ 3 个小节的页面生成 ≥ 2 个图表”可能会导致在小的、以正文为主的页面上出现低质量图表。我们应该观察并在需要时放宽规则 —— 该规则是可调的。
5. **父页面架构断言验证虽然是确定性的，但很脆弱**。如果依赖图错误（罕见但可能发生），假阴性就会漏掉。缓解措施：当依赖图查找与父页面断言的关系矛盾时记录警告，以便用户发现图 bug。
6. **第 1 版中没有显式的 Gemini 上下文缓存**。在 Gemini 上拥有超大型仓库的用户可能想要显式的 `cachedContents`。如果需求出现，将进行后续工作。

## 13. 总结

本设计将单阶段页面生成器替换为四阶段流程（大纲 → 草稿 → 事实检查 → 有条件修订），增加了快速模型分离以保持成本持平，扩展了 LLM 提供商接口以支持提示词缓存，在检索层对陈旧文档进行降权，扩展了支持的 Mermaid 图表调色板，并强制每个图表采用一致的标题/源码格式。结果是在成本大致相同且延迟增加可控的情况下，显著提高了接地性和图表多样性。
